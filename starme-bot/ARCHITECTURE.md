# StarMe AI — архитектура

## Цель

Создать персональное фото клиента в сцене, взятой с фото знаменитости, **не ломая** композицию оригинала и не требуя от клиента промптов.

Ключевая идея: разделить **сцену** и **личность**. Сцена описывается структурированным JSON-дизайн-кодом, личность — селфи клиента. Дизайн-код — это описание, а не команда: реальный результат зависит от способности генератора работать с референсами.

## Поток

```
[Telegram]
   │ 1. photo ( celebrity / scene )
   ▼
core.handlePhoto ──▶ store.saveImage(scene) ──▶ analyzer.analyze()
                                                  │
                                    ┌─────────────┘
                                    ▼
                          JSON design code ( + scene reference )
                           сохраняется в сессии
                                    │
   │ 2. photo ( selfie )
   ▼
core.handlePhoto ──▶ [optional selfieGuard] ──▶ generator.render(
                                                              designCode,
                                                              selfie,
                                                              sceneRef)
                                                  │
                                                  ▼
                                       готовое фото → клиент
```

## Компоненты

| Компонент | Ответственность |
|---|---|
| `src/bot.mjs` | Telegram (Telegraf): приём фото, скачивание, отправка результата |
| `src/core.mjs` | Машинa состояний двухэтапного пайплайна (не зависит от Telegram, тестируется локально) |
| `src/scene.mjs` | Схема дизайн-кода, валидация, нормализация, сборка промпта, анализаторы |
| `src/generator.mjs` | Абстракция генератора + адаптеры (mock / FaceFusion / InstantID) + guard |
| `src/store.mjs` | Хранилище сессий и изображений (JSON, атомарная запись) |
| `src/factory.mjs` | Сборка analyzer + generator + guard по конфигу |
| `worker/*.py` | Реальные модели, HTTP-сервер по единому протоколу |

## Дизайн-код (JSON schema, v1)

```json
{
  "version": 1,
  "scene": {
    "composition": "cinematic close-up portrait",
    "camera_angle": "slightly turned three-quarter view",
    "head_position": "head tilted slightly to the left",
    "expression": "confident, natural expression",
    "lighting": "soft directional movie lighting",
    "background": "original background preserved",
    "color_grading": "warm cinematic tones"
  },
  "identity": { "source": "client_selfie", "preserve_identity": true },
  "constraints": {
    "preserve_pose": true,
    "preserve_clothing": true,
    "preserve_background": true,
    "match_lighting": true
  }
}
```

- `scene` — что видно на фото (без личности).
- `identity` — всегда `client_selfie`; личность не может быть частью шаблона.
- `constraints` — какие сходства с оригиналом важны генератору.

Валидация строгая: генератор получает только корректный код (`validateDesignCode`).

## Генератор — ключевой компонент

Two modes, и выбор зависит от приоритета.

### Mode A — FaceFusion (swap)

- Что делает: меняет лицо в фото сцены на лицо клиента.
- Вход: `scene_image` + `identity_image` (селфи).
- Результат: максимально близко к оригиналу (поза, одежда, фон, свет).
- Дизайн-код: хранится и переиспользуется, но не ведёт генерацию.
- Сложность: низкая (`pip install facefusion`), работает на CPU, но для качества нужен GPU.
- Подходит для: быстрого старта, верности оригиналу.

### Mode B — InstantID (regenerate)

- Что делает: генерирует новую сцену по тексту, сохраняя личность.
- Вход: `prompt` (из дизайн-кода) + `identity_image` + `scene_image` (поза через IdentityNet).
- Результат: сцена пересоздана; поза берётся из референса, но фоне/одежде может отличаться.
- Дизайн-код: реально ведёт генерацию (через промпт).
- Сложность: высокая (SDXL, torch, веса), требует GPU.
- Подходит для: переиспользования шаблона без хранения фото, вариативности.

### Что выбрать

- Для продукта, где важна верность конкретному фото → **FaceFusion**.
- Для продукта, где важна переиспользуемость шаблона и вариативность → **InstantID**.
- Идеальный вариант — оба: swap как «точное», InstantID как «творческое» направление.

### Cloud-вариант — Replicate

Если нет GPU и не хочется настраивать workers: Replicate идёт как генератор в Bot. При регистрации ~$10 бесплатных кредитов, одна фотография ≈ $0.0016. Нужен только ключ API (`REPLICATE_API_TOKEN`). Подходит, чтобы запустить продукт без инфраструктуры; для масштаба лучше локальный worker.

Бесплатность: FaceFusion и InstantID — open source, локальные, без API-ключей (затраты — железо). Replicate — облачный, поиюе-поиспользованию, с бесплатным кредитом на старт.

## Анализатор сцены

- `heuristic` — offline, плейсхолдер. Не видит содержание, только размер/формат. Для демо и тестов.
- `vlm` — vision-модель (OpenAI-compatible). Возвращает JSON в нужной форме. Для реального понимания сцены нужен VLM; можно использовать бесплатные/локальные (Ollama, LM Studio, vLLM) или облачный с лимитом.

## Протокол worker (HTTP)

```
POST {worker}/render
{
  "mode": "swap" | "instantid",
  "prompt": "...", "negative_prompt": "...",
  "identity_image": "<b64>", "scene_image": "<b64>",
  "params": { ... }
}
-> { "image": "<b64>", "mime": "image/jpeg", "generator": "..." }

POST {worker}/analyze
{ "image": "<b64>" }
-> { "faces": 1, "has_face": true }
```

Node-бот не знает о моделях — только о этом протоколе. Модель можно менять без изменения бота.

## Защита от злоупотреблений

1. **Отдельный этап**: селфи принимается только после создания шаблона.
2. **Guard**: `STARME_SELFIE_GUARD=face` → воркер `/analyze` отклоняет селфи без лица.
3. **Референс хранится**, но не отдаётся напрямую (`/scene` только подтверждает наличие).
4. **Повторная генерация без смены лица**: после начала рендера дизайн-код и селфи зафиксированы в сессии.
5. **Очистка**: можно добавить поovarié для удаления `data/images` по TTL (оригиналы не хранятся вечно).
6. **Consent**: важно иметь согласие на использование внешности и соответствие правилам платформы/юрисдикции. Liveness-проверка (случайное действие) усложняет использование чужих фото, но не даёт абсолютной защиты.

## Хранение и состояния

- Сессии: `data/sessions/<user>.json` — stage, designCode, ссылки на изображения.
- Изображения: `data/images/{scene,selfie,result}/...`.
- Атомарная запись (tmp + rename) для избежания повреждений.

## Сбор и продакшн

- Worker выносится в отдельный процесс/сервер (GPU-хост).
- Для нескольких пользователей: СУБД вместо JSON-файлов, очередь задач (BullMQ/RabbitMQ), отдельные машины для worker.
- Rate limiting и квоты на генерацию.
- Мониторинг ошибок генератора/анализатора.

## Ограничения

- JSON — это описание, не фото. Для верности нужен референс-оригинал.
- `heuristic` анализатор не «видит» сцену — для реального продукта нужен VLM.
- Liveness-проверка — смягчение, не абсолютная защита.
